## 1. Inventor の拡張方法と、なぜアドインなのか

Autodesk が公開している [Inventor API の概要](https://aps.autodesk.com/ja/developer/overview/inventor-api)
が挙げているのは **COM API / VBA / Apprentice** の 3 つ。
実際に使う入れ物としては、これに **アドイン** と **iLogic** が加わる。

| 方式 | 実体 | UI | 用途 |
|---|---|---|---|
| **アドイン** | コンパイル済み DLL。起動時に自動ロード | **リボンに独自タブを出せる**。イベントも取れる | ← **採用** |
| iLogic ルール | ソースファイル。実行時にコンパイル | 無し。iLogicブラウザからダブルクリック | その場限りの自動化 |
| VBA | Inventor 内蔵のマクロ | 無し | 使い捨ての操作 |
| Apprentice | Inventor 無しで動く COM サーバー | 無し | 外部ツールからファイルを読む |

**重要**: これらは別々の API ではない。**どれも同じ COM API を呼んでいる**。
たとえば STL 書き出しのコードは、iLogic で書いてもアドインで書いても中身は同じ:

```csharp
app.ApplicationAddIns.ItemById[StlExporter.TranslatorAddInId]  // TranslatorAddIn を取得
translator.SaveCopyAs(source, context, options, medium);       // STL 書き出し
doc.AllReferencedDocuments                                     // 参照ドキュメント走査
```

違うのは中身ではなく**パッケージング**。このプロジェクトは当初 iLogic 外部ルールで
実装していたが、リボンから 1 クリックで使えるようにするためアドインへ移行した。
ロジックはほぼそのまま移植できている。

### アドインの読み込まれ方

Inventor は起動時にアドインフォルダの `.addin`(XML)を読み、
`<ClassId>` に書かれた GUID を持つクラスを `<Assembly>` の DLL から探して生成する。

**COM への登録(regasm)は不要。** これが分かっていないと無駄にハマる。
必要なのは以下の 3 つが一致していることだけ:

1. `src\RichInventor.addin.template` の `<ClassId>` / `<ClientId>`
2. `StandardAddInServer.cs` の `[Guid(...)]`
3. `<Assembly>` が実在する DLL を指していること(`Install-AddIn.ps1` が絶対パスを埋める)

## 3. 落とし穴(全部ここで踏んだもの)

### 3.1 Inventor 名前空間は .NET の基本型と名前が衝突する

`Inventor` 名前空間には **`File` / `Path` / `Environment` / `Color`** といった型がある。
`using Inventor;` を書いたファイルでは、これらが `System.IO.File` などと
曖昧参照になりコンパイルが通らない。

```
error CS0104: 'Path' は、'Inventor.Path' と 'System.IO.Path' 間のあいまいな参照です
```

→ `GlobalUsings.cs` でエイリアスを 1 回だけ宣言して解決している。
**エイリアスは using ディレクティブより優先される**ので、これでプロジェクト全体に効く。

```csharp
global using File = System.IO.File;
global using Path = System.IO.Path;
global using Directory = System.IO.Directory;
global using Environment = System.Environment;
```

Inventor 側の型が要るときは `Inventor.Path` と明示的に書く。
新しく衝突する名前が出てきたら、このファイルに 1 行足すだけでよい。

> 同じ問題は VB でも起きる。VB には global using が無いので、
> `System.IO.Path.Combine(...)` のように毎回完全修飾するしかなかった。

### 3.2 `.ps1` は UTF-8 **BOM 付き** で保存する

BOM が無いと PowerShell 5.1 が ANSI(Shift-JIS)として読み、日本語コメントが化けて
**パースエラーで動かなくなる**。このプロジェクトで 2 回踏んだ。

```
You must provide a value expression following the '-' operator.
Unexpected token '繝薙Ν繝我ｸｭ' in expression or statement.
```

C# ソースは .NET SDK が UTF-8 を前提にしているので BOM 無しで問題ない。
**`.ps1` だけ**注意すればよい。直すなら:

```powershell
$utf8bom = New-Object System.Text.UTF8Encoding($true)
$t = [System.IO.File]::ReadAllText($path, (New-Object System.Text.UTF8Encoding($false)))
[System.IO.File]::WriteAllText($path, $t, $utf8bom)
```

### 3.3 `SaveCopyAs` は黙って失敗することがある

例外を投げずに、ファイルだけができていないことがある。
`StlExporter.ExportDocument` では書き出し後に `File.Exists` で確認している。
新しい書き出し系を足すときも同じようにすること。

### 3.4 ButtonDefinition のイベントは直接は繋げない

`Inventor.ButtonDefinition` インターフェースには `OnExecute` が生えていない。
イベントは別インターフェースにあるので、キャストしてから購読する:

```csharp
((ButtonDefinitionSink_Event)button).OnExecute += handler;
```

さらに **ハンドラのデリゲートをフィールドで保持すること**。
ローカル変数のままだと GC されてボタンが無反応になる(`RichCommand._handler`)。

### 3.5 COM のコールバックに例外を投げ返さない

`OnExecute` から例外が Inventor 側に伝播すると Inventor が不安定になる。
`RichCommand.OnExecuteInternal` で必ず捕まえてダイアログにしている。
新しいコマンドは `RichCommand` を継承すればこの受け止めが自動で付く。

### 3.6 .NET 8 では `Marshal.GetActiveObject` が無い

起動中の Inventor に外から繋ぐ定番のコードが .NET 8 では使えない。
`oleaut32.dll` の `GetActiveObject` を P/Invoke する
(`RichInventor.Probe/Program.cs` に実装がある)。

### 3.7 ダイアログには親ウィンドウを渡す

親を指定しないと、ダイアログが Inventor の裏に隠れて操作不能になることがある。
`Dialogs` は `app.MainFrameHWND` を親にしている。

### 3.8 リボンは再ロードすると重複しうる

Inventor はリボン構成をユーザープロファイルに保存する。
`RibbonBuilder` はタブ・パネル・ボタンすべてを「あれば使う、無ければ作る」で
処理している。`firstTime` フラグには依存していない(リボンをリセットされても復活するため)。

## 4. 開発の進め方

### 4.1 ビルドと登録

```
powershell -ExecutionPolicy Bypass -File tools\Install-AddIn.ps1
```

ビルド → `.addin` を `%APPDATA%\Autodesk\Inventor 2025\Addins\` に配置、まで一発。
**Inventor が起動していると DLL がロックされてビルドに失敗する**ので、先に終了すること。

### 4.2 Inventor で確認

Inventor を起動し、リボンの **[RichInventor]** タブを開く。
タブが出ない場合は **[ツール]** → **[アドイン]** で読み込み状態とエラーを確認する。

### 4.3 Inventor を再起動せずに確かめる

アドインの動作確認はどうしても Inventor の再起動が要るが、**Core のロジックだけなら
再起動せずに確かめられる**。検証用コンソールがアドインと同じクラスを参照している。

```
dotnet build src\RichInventor.Probe\RichInventor.Probe.csproj -c Release
cd src\RichInventor.Probe\bin\Release

RichInventorProbe.exe scan             いま実行したら何が書き出されるか(書き出さない)
RichInventorProbe.exe export <dir>     実際に 3DP 部品を書き出す
RichInventorProbe.exe icons <dir>      リボンアイコンを PNG に出す(見た目の確認)
RichInventorProbe.exe groundscan       最大平面を接地で選ばれる面と判定を出す(拘束しない)
RichInventorProbe.exe ground           アクティブなアセンブリに実際に接地拘束を付ける(Ctrl+Z 1 回で戻る)
RichInventorProbe.exe groundscan selected / ground selected   選択部品だけを対象にする
```

> Inventor がアドインの `bin\Release\RichInventor.dll` を掴んでいるとビルドがコピーで失敗する。
> そのときは `-p:OutputPath=<別フォルダ>\` を付けて別の場所にビルドする(`Install-AddIn.ps1` と同じ方法)。

`scan` は起動中の Inventor につないで、STL トランスレータの状態・アクティブドキュメント・
開いているパーツ数・選択中の部品・`3DP` 部品の一覧を出す。
**新しい機能を足したら、まずここで動かしてからリボンに載せると早い。**

### 4.4 Inventor API の挙動を調べたいとき

PowerShell から起動中の Inventor に COM で繋いで直接叩ける
(PowerShell 5.1 は .NET Framework なので `Marshal.GetActiveObject` が使える)。

```powershell
$inv = [System.Runtime.InteropServices.Marshal]::GetActiveObject("Inventor.Application")
$inv.ActiveDocument.AllReferencedDocuments.Count
```

列挙型の実際の数値や、メソッドのシグネチャを知りたいときは interop を反射する:

```powershell
$asm = [System.Reflection.Assembly]::LoadFrom("C:\Program Files\Autodesk\Inventor 2025\Bin\Autodesk.Inventor.Interop.dll")
[int][Inventor.IOMechanismEnum]::kFileBrowseIOMechanism   # -> 13059
$asm.GetType("Inventor.RibbonTabs").GetMembers() | ? { $_.Name -eq "Add" }
```

リボン系のシグネチャは引数が多く間違えやすいので、書く前にこれで確認するとよい。

## 5. 新しい機能の足し方

リボンにボタンを 1 個増やす手順。

1. `Commands/` に `RichCommand` を継承したクラスを作る

```csharp
public sealed class MyCommand(Inventor.Application app) : RichCommand(app)
{
    public override string InternalName => "RichInventor:MyCommand";  // 一意にする
    public override string DisplayName  => "機能名";
    public override string Description  => "リボンのツールチップに出る説明";
    public override string ToolTip      => "短い説明";

    protected override Bitmap CreateIcon(int size) => IconFactory.MyIcon(size);

    protected override void Execute()
    {
        var doc = App.ActiveDocument;
        // ... 対象を集める ...
        // ... RunExport(targets, folder, Options.ToStlSettings(), "見出し") ...
    }
}
```

2. `UI/IconFactory.cs` にアイコンを描くメソッドを足す
3. `StandardAddInServer.Activate` の `_commands.Add(...)` に 1 行足す
4. 複数のコマンドで使い回せる処理になったら `Core/` へ移す
5. `RichInventorProbe.exe scan` で動きを確認してから Inventor を再起動する
6. `README.md` の機能一覧表と `docs\仕様書.md` に追記する

**書き方の作法**(既存コードに合わせる):

- 例外は `RichCommand` が受け止めるので、`Execute()` の中では素直に投げてよい
- 1 件失敗しても続行し、最後にまとめて報告する(`ExportResult`)
- 上書きや削除の前には必ず確認をとる
- 調整したい値は `AddInOptions` に足す(再ビルドなしで変えられる)
- 日本語のメッセージは「何が起きたか」と「どうすればよいか」を両方書く

## 6. 検証状況

### 実機で確認済み(Inventor 2025.4)

- **STL 書き出しが実際に動くこと。**
  `MeasureEncoderUnit_all_v2.iam` の `3DP` 部品 4 件を検証ツールから書き出し、
  生成された STL を解析して確認した:

  | ファイル | 三角形数 | バイト数 | 寸法 (mm) |
  |---|---|---|---|
  | `3DP_BenzSpacer.stl` | 2800 | 140084 | 27.998 × 27.999 × 1.500 |
  | `3DP_MountGide_v2.stl` | 2372 | 118684 | 19.000 × 4.000 × 40.000 |
  | `3DP_Spacer_MountPachiAMT_v2.stl` | 2654 | 132784 | 5.200 × 5.200 × 5.520 |
  | `3DP_Spacer_RainforceBread_v2.stl` | 3222 | 161184 | 5.199 × 5.200 × 30.200 |

  バイト数はすべて `84 + 三角形数 × 50` に一致 = 正しいバイナリ STL。

- STL トランスレータのオプション名と値(→ [仕様書 2.2](仕様書.md#22-stl-トランスレータのオプション値実測))
- `AllReferencedDocuments` が再帰的かつ重複なしであること(35 件 / うち `3DP` 4 件)
- `Views.Count` で「ユーザーが開いたパーツ」と「参照で裏読みされたパーツ」を区別できること
- アイコンの `IPictureDisp` 変換が .NET 8 の `AxHost` で成功すること
- 設定ファイルが既定値で自動生成され、読み書きできること
- アドインと検証ツールの両方が警告 0・エラー 0 でビルドできること

### 未検証

- **Inventor を再起動してリボンに [RichInventor] タブが出るところ。**
  アドインは起動時にしか読み込まれず、作業中の Inventor を落とせなかったため。
  最初の 1 回だけ、Inventor 再起動後にタブとボタンの表示を確認すること。
  もし出なければ **[ツール]** → **[アドイン]** で読み込みエラーを確認する。
